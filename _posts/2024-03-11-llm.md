### 概念

* 原始模型只是续写。Instruct版每个模型有不同的prompt模板，主流是ChatML
* 采样参数
  * temperature和top_p和top_k：调小会更保守更有确定性，调大会有创意更发散。一般只调其中一个。例如对于答案是唯一确定的场合（翻译）temp用0-0.3，写文章用0.5，写广告用0.7
    * 原理：先用topK=n表示选出词表中概率最高的n个token（假设为3，选出了A B C且概率分别为.3 .2 .1），再累加概率直到满足topP（假设为.5，则会留A B），再根据温度指定的随机程度选
  * repetition_penalty：好像一般设为1.05。llama.cpp里叫--repeat-penalty
  * frequency_penalty和presence_penalty：后者是一直有效的，增大则会减少输出已存在过的词的概率，有助于讨论新主题；前者惩罚频繁使用的词，但仍可能从AAA变到ABABAB
* dtype
  * FP32：就是普通的float。FP16：精度稍差，数字范围变为±65000。BF16：精度更差，但保留了FP32的数字范围，只有3060后才支持，IntelXeon3rd也支持。混合精度：平常用FP16，在加法用32。TF32：只有A100支持
  * torch_dtype：pytorch在不指定时会默认转换到float32。预训练模型指定auto会从参数中读取，一般是torch.bfloat16。在CPU上bf16是float32的2倍耗时，float16是float32的12倍耗时，不知道是不是因为模型本身是bf16的缘故
    * 查看类型：next(model.parameters()).dtype 或 pipe.torch_dtype
  * 大多数游戏GPU，FP64的性能是FP32的1/32
* output tokens：对于prompt的单次最大输出，如16k。context window：input+output的最大长度，如128k
  * 显示token划分：https://platform.openai.com/tokenizer 本地用库计算历史可避免超限
  * 输入的token不太影响延迟，而长输出会影响，因为原理上token是一个个产生的
  * 要求结构化输出时减少token的一种方式：将长字段描述改为注释，这样就不用生成
  * 对内存带宽有要求，比如8B模型按float16加载就占16GB，每生成一个token就要读取16GB（MOE看激活参数大小）

## PromptEngineering

* C.O.S.T.A.R. 框架：Context背景信息 Objective目标任务 Style写作风格 Tone语气（正式、友好、幽默） Audience受众（The output should be at a reading level for a 12-year-old） Response Format响应格式
* In the context of xxx, 实际问题。Act as an expert on xxx。减少输出：be very brief/concise
* 区分指令和内容：Summarize the text **delimited by triple backticks(quotation/XML marks)** into a single sentence
* 结构化输出
  * Provide content in JSON format with the following keys: aaa, bbb
  * Foramt your response as a list of items separated by commas
  * Respond only with code, and with no markdown formatting 或 Return only the code in your reply. Do not include any additional formatting, such as markdown code blocks
* 检查条件：If the text contains xxx, action. If not, simply write \"No info provided.\"
* few shot 续写（使用例子保持一致格式）：Your task is to answer in a consistent style. <角色A>: xxx. <角色2>: xxx
* 提供参考文本，要求将提供的材料原文引用出来，可减少幻觉
  * Use the below article about xxx to answer the subsequent question. If the answer cannot be found, write "I don't know."
* meta-prompt：一个用来创建或修改prompt的prompt，一般各产品的Agent中提供了此功能。OpenAI给出的版本：见docs中的prompt-generation
* COT：think step by step、explain your reasoning。但对于o1不需要，它可用Only supply your reasoning at the beginning and end, not throughout the code. Make a plan for the directory structure you'll need, then return each file in full
  * 反思：现在存在两个角色，翻译家将英文翻译成中文，保留原本意思；校对家对于原文和译文找出不足之处并按中文习惯润色。步骤：先输入原文，翻译家翻译输出，校对家再输出

## transformers

* 安装：transformers accelerate。后者用于device_map='auto'，会自动选用cpu或cuda，支持多张显卡，显存不够时会自动用内存。不会自动装torch
* pipeline支持的任务：https://hf.co/docs/transformers/main/zh/task_summary
  * text-generation：又叫Causal Language Modeling。包括聊天机器、完成句子、内容生成。是decoder-only架构，包括GPT、Llama、Mistral、Falcon
  * Text-to-Text Generation：又叫Sequence-to-Sequence Modeling、ConditionalGeneration。包括翻译、问答、总结、自动更正。是encoder-decoder架构，包括T5、BART、Marian
    * 与GPT的区别：必须在特定任务（给一个固定内容的前缀Prompt）上微调。参数需求更小。不适合多轮对话
    * 原始T5仅支持英语，多语言的叫mT5；byt5不用token，直接用byte。FLAN-T5是新版，在任何方面都更好，但不是多语言的；其他人微调的：LaMini-Flan-T5-77M。其他代替：bigscience/mt0-small
  * Encoder-only：包括Bert。用于分析内容，如情感分析、主题分类、信息提取

### pipeline使用

```py
from transformers import pipeline

model_id = '本地模型文件夹' # 也称为checkpoint
pipe = pipeline('text-generation', model_id, torch_dtype='auto', device_map='auto') # kwargs会应用到后续调用中，包括通用参数和特定任务参数
# pipe()的第一个参数是inputdata；也能接受迭代器返回迭代器，此时一般还调整batch_size，但仅当输入长度差不多时才会加速，否则因为对齐可能减速

user_input = 'Who are you'
message = [
    {'role': 'system', 'content': 'You are a helpful assistant.'},
    {'role': 'user', 'content': user_input}
]

outputs = pipe(message, max_new_tokens=256, do_sample=True, temperature=0.5) # 默认do_sample=False相当于temperature=0
text = outputs[0]['generated_text'][-1]['content']

# 继续对话
chat = outputs[0]['generated_text'] # 包含了所有历史
chat.append({'role': 'user', 'content': user_input})

# 界面
import gradio as gr
gr.Interface.from_pipeline(pipe).launch()
```

### 手动创建使用

```py
model = AutoModelForCausalLM.from_pretrained(model_id).to(device)
  # 支持加载并转换tf模型到pt：from_tf=True
tokenizer = AutoTokenizer.from_pretrained(model_id)

formatted_chat = tokenizer.apply_chat_template(message, tokenize=False, add_generation_prompt=True)
inputs = tokenizer.apply_chat_template(message, return_tensors='pt', add_generation_prompt=True, return_dict=True).to(device)
  # tokenize 默认True，仅得到input_ids，相当于tokenizer.encode()。若用True一般再加return_dict=True，则与传给tokenizer()一样，可省下一步
  # add_generation_prompt 添加 `<|im_start|>assistant\n`。训练期间不要用
  # continue_final_message 当最后一条聊天记录是assistant的时，让其续写而非回复。不能与上一条同用
  # TextGenerationPipeline的默认行为：当最后一条聊天记录是user时，设置add_generation_prompt=True；如果是assistant，设置续写

inputs = tokenizer(formatted_chat, return_tensors='pt', add_special_tokens=False).to(model.device)
  # 第一个参数接受list或str。若为list(即batch推理)，要加padding_side="left"统一长度
  # 返回值为{input_ids, attention_mask}，它们都是二维tensor(即list[向量化的msg]、相同长度的全1)
    # 有时a可从前者自动推断出来，如果不行，会报warning说结果不可信
  # tokenizer.pad_token = tokenizer.eos_token 当batch推理时使用，因为大部分LLM没有pad_token
  # add_special_tokens 默认情况下，一些分词器会添加<bos>和<eos>等特殊标记；聊天模板中应已加，此处再加不正确。如果应用聊天模板时用tokenize=True则无需担心

outputs = model.generate(**inputs, max_new_tokens=99)
  # 所有生成的默认值可在GenerationConfig(generation_config)里指定
  # max_new_tokens 默认20，一般要指定否则基本无法输出
  # do_sample在这一步 TODO:改为True后其他参数的默认值
  # 调用model() 不用generate，效果是生成一个词

text = tokenizer.decode(outputs[0][inputs['input_ids'].size(1):], skip_special_tokens=True)
  # outputs 一般取[0]获得唯一的响应。截取去掉输入的prompt，decode。如果输入了多条消息，用batch_decode()
  # skip_special_tokens 用于去掉<|im_end|>

# 流式
from transformers import TextStreamer
streamer = TextStreamer(tokenizer, skip_prompt=True, skip_special_tokens=True) # 重用
model.generate(..., streamer=streamer)
```

## 量化

* 分类
  * 训练后量化(Post Training Quantization, PTQ)：量化预训练好的模型
    * weight only、dynamic、static
  * 量化感知训练(Quantization Aware Training, QAT)：在训练或进一步微调之前执行量化。如QLoRA（就是量化+LoRA）
    * 目前的量化算法基本都能配合PEFT。但quanto除外，https://github.com/huggingface/peft/issues/1997
  * 有一种说法是QAT需要大量训练成本，对于LLM不能接受
* 效果：AWQ > GPTQ > bnb
* GPTQ(AutoGPTQ, auto-gptq)采用int4/fp16 (W4A16)的混合量化方案，模型权重被量化为int4，而激活值则保留在float16。在推理阶段，模型权重被动态地反量化回float16。也支持int8
* AWQ：仅有int4，torch_dtype仅为float16。推理时最好使用AutoAWQForCausalLM.from_quantized()，具有合适的默认参数。支持CPU推理(use_ipex)
  * https://qwen.readthedocs.io/zh-cn/latest/quantization/awq.html
* bitsandbytes(bnb)：可用于非文本（多模态）模型，可在线量化（On the fly）无需先单独转换（但也可以保存）。简单，零样本。之前仅支持cuda，现在正在重构支持多后端，包括CPU
  * BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_use_double_quant=True, bnb_4bit_compute_dtype=torch.bfloat16)
* optimum-quanto(不要装quanto包)：HF出的，兼容torch.compile，支持cv模型，支持在线量化，支持CPU。HF网页文档与github上的不同，如果直接用pytorch或想保存则看后者
  * 不支持MinGW，实际是因为pytorch不支持；其中将IS_LINUX=True且IS_WINDOWS=False更有希望，将一处`replace(':', '$:')`启用后，ninja的构建报找不到`torch/extensions.h`，但明明参数里已经有了`-isystem xxx/torch/include`且单独运行找得到。另外调试时中断会导致Lock文件不删除无限等待
  * 无法与peft一起使用
* optimum-intel
  * 具有三个子项目neural-compressor、openvino、ipex。但感觉作用都差不多，都是量化成自己的格式，再替换某个import运行。前两者还说可以剪枝和知识蒸馏
  * Neural Compressor：optimum-cli inc quantize。基于块结构化稀疏性，支持主流DL框架；支持Intel硬件，通过onnx支持其他GPU。安装依赖非常多，光本体就会装pillow opencv pandas scikit-learn
  * openvino：optimum-cli export openvino 转换到openvino格式，可以顺便量化。对于openvino来说专注于推理
    * quantization_config=OVWeightQuantizationConfig(bits=4,quant_method='awq')
    * 特别提到了支持SD
  * 另有onnxruntime不在intel下但在optimum下
    * 转换模型到onnx：https://huggingface.co/docs/transformers/serialization
* intel/auto-round：自己宣传比awq好。Neural Compressor中集成了此算法。依赖peft
* pytorch/ao：torchao
* AQLM：量化成1b和2b，支持cpu和torch.compile，不支持在线量化。pip install aqlm[cpu] 依赖numba

#### tokenize化

* token_type_ids：类似于attention_mask，作用是当调用tokenizer(s1, s2)时，分辨哪个部分是第二个句子

```py
# 小数据手动处理：
model_inputs = tokenizer(ds['text'], padding='longest')
labels = tokenizer(ds['target'], padding='longest') # TODO: encode不行
model_inputs['labels'] = labels['input_ids']
tokenized_dataset = Dataset.from_dict(model_inputs)

# 正常手动处理
def preprocess_fun(examples): # examples: {inputs:[], outputs:[]}
    model_inputs = tokenizer(examples['inputs'],
        max_length=max_input_length, truncation=True, padding='max_length' # max_input_length是预定义固定值，超出的截断，少的填充；如果不指定，padding='max_length'会填充到模型最大支持长度
        # 另一种做法：padding='longest' 根据batch中的内容自动计算；后续Collator还会填充到它那batch的最长
        # 另一种做法：此处不padding（默），在Trainer中用DataCollatorWithPadding动态填充到batch中的最长样本
    )
    # 把target也向量化，但只要用到id
    labels = tokenizer(..., max_length=max_target_length)
    model_inputs['labels'] = labels['input_ids']

    # 对于Seq2Seq（T5）：如果进行了填充，必须将pad替换为-100，使得交叉熵损失函数不计算pad
    model_inputs["labels"] = [
        [(label if label != tokenizer.pad_token_id else -100) for label in labels_example]
        for labels_example in model_inputs["labels"] # 遍历批次中的每一个标签序列
    ]

    return model_inputs
ds = ds.map(preprocess_fun, batched=True) # 如果存在FastTokenizer（tokenizer.is_fast），不需要指定num_proc
```

#### DataCollator

* 动态填充
* 创建Trainer时传递，不传（且未指定processing_class）时用default_data_collator
* 大多数NLP任务（序列分类、问答），输入序列长度不同，用DataCollatorWithPadding。指定processing_class后自动用此项
* 对于Bert的MLM：DataCollatorForLanguageModeling。它能自动随机masking token
* 对于Seq2Seq（翻译、总结）：DataCollatorForSeq2Seq，它会将labels中的pad token替换为-100

### 函数(工具)调用

* 按指定格式将函数信息写成schema，传给create的tools参数。如果LLM决定调用tool，finish_reason等于'tool_calls'，message.tool_calls[0]指定了要在本地调用的函数名、参数、id；好像没有一般的回复。保存历史纪录user和{role:tool, content:函数输出, tool_call_id}，再chat
* f1={name, strict:true, description, parameters{type:object, properties{argname{type, description, 可选enum限制参数值}}, required[argname]}}; tools=[{type:function, function:f1}]
  * 其他创建方式：openai.pydantic_function_tool、transformers.utils.get_json_schema
* 默认支持“并行调用”，即可能调用多个函数。还可设置强制调用和不调用
* https://github.com/openai/swarm 是chat.completions的封装。功能一：方便创建函数调用，不用自己写schema。功能二：若return另一个Agent，则可创建类似pipeline的处理过程
* 本质还是把函数信息生成某种prompt，存在许多问题。可以在system_prompt里写用户询问某些问题时(何时)调用某个函数、在调用f1之前先调用f2
* 结构化输出，是JSON模式的改进：分为工具调用的参数(本质是LLM输出了那些参数)和一般的响应(指定response_format)。对于PySDK，都能用Pydantic自动生成，见openai-python的helpers.md，有个beta的parse()是create的包装，自动处理返回值生成指定类型在message.parsed。如果拒绝回答，信息在refusal里
  * JSON模式：response_format={"type":"json_object"}且必须在system_prompt中要求以JSON格式回答

## Agent理论

* LLM（多个协作） + 记忆（长期如Rag微调、短期如上下文） + 规划（推理） + 使用工具。模拟人类完成任务，（感知）根据环境做出不同规划

### MCP

* 统一规定了一个服务端程序(MCP Server)如何处理tool_calls的输入和返回自定义逻辑的处理结果
* 客户端分别与LLM和MCPS交互，先连接MCPS（可以同时连接多个），调用list_tools()获得它支持的工具。整理工具元数据发给LLM，让它决定调用哪个。再按计划调用call_tool('工具名',{参数})
* 如果由第三方写好MCPS，则相当于做好了工具，LLM Client在与LLM交互完后只要调用不用实现
* LLM Client与MCPS不必处于同一台机器上，现在一般就在一台机器上，且通过stdio交互
* 其他功能
  * Prompt模板：由MCPS提供提示词。包括获取模板列表和内容
  * Resources：逻辑上，预定义了一些存在于服务端的资源（文本等），用户能在UI上查看内容、选择使用
  * Root：客户端向服务端公开“根”目录，服务端可以列出。当根更改时，客户端通知服务端
  * Sampling：服务端在处理过程中“询问”客户端，客户端添加回调处理逻辑，可直接回复，**也可调用LLM**再回复。这使得Server不必运行LLM就能利用其功能，还能作为类似Agent
  * 分页：服务端在需要分页时会加上nextCursor字段，它对客户端是不透明的乱码字符串，而不是数字；客户端在后续调用中传递
* 最近的规范允许用普通HTTP了，之前只允许SSE
